# Описание проекта Cinema

## 1. Назначение проекта

Проект `Cinema` представляет собой веб-систему для просмотра киноафиши, выбора сеансов, бронирования мест и оформления заказа на билеты в кинотеатр. Система реализована как Django-приложение с веб-интерфейсом, REST API и дополнительным Telegram-модулем.

Основная задача проекта состоит в автоматизации процесса выбора и покупки билетов. Вместо работы только через кассу пользователь может самостоятельно:

- просматривать список фильмов;
- фильтровать фильмы по жанрам, возрастному ограничению и поисковому запросу;
- открывать детальную страницу фильма;
- смотреть доступные сеансы;
- выбирать места в зале;
- оформлять заказ;
- переходить к оплате;
- просматривать историю заказов в личном кабинете;
- при необходимости связывать аккаунт сайта с Telegram.

Проект предназначен для:

- обычных пользователей кинотеатра;
- администраторов и менеджеров, которые управляют фильмами, сеансами, залами, заказами и билетами;
- разработчиков и преподавателей, которые проверяют архитектуру и бизнес-логику учебного Django-проекта.

Для курсовой работы проект подходит хорошо, потому что в нём есть:

- полноценная предметная область;
- набор связанных моделей базы данных;
- пользовательский веб-интерфейс;
- авторизация и личный кабинет;
- работа с заказами и статусами;
- интеграция внешних сервисов;
- отдельный API-слой;
- дополнительный Telegram-модуль;
- демонстрация как синхронной, так и расширенной фоновой логики.

## 2. Актуальность проекта

Тема проекта является актуальной, так как продажа билетов и бронирование мест в кинотеатрах давно перешли в цифровой формат. Пользователь ожидает, что сможет выбрать фильм, удобный сеанс и конкретные места без посещения кассы.

Актуальность проекта проявляется в следующих аспектах:

- автоматизация процесса продажи билетов;
- снижение нагрузки на кассу и сотрудников кинотеатра;
- возможность самостоятельного выбора мест пользователем;
- повышение удобства и скорости обслуживания;
- хранение истории заказов в личном кабинете;
- возможность интеграции онлайн-оплаты;
- дополнительный канал доступа к данным через Telegram.

С практической точки зрения проект демонстрирует типичную информационную систему сферы услуг, где есть каталог сущностей, пользовательские действия, статусы, права доступа, платежная логика и интеграция со сторонними сервисами.

## 4. Роли пользователей

В проекте можно выделить несколько ролей.

### 1. Гость

Гость может:

- открыть главную страницу;
- просматривать фильмы;
- искать и фильтровать фильмы;
- просматривать сеансы;
- смотреть детальные страницы фильмов и сеансов;
- открывать страницы регистрации и входа;
- использовать публичные API-методы чтения.

Гость не может:

- покупать билеты;
- просматривать личный кабинет;
- видеть свои заказы;
- создавать заказы через API;
- редактировать данные системы.

### 2. Авторизованный пользователь

Авторизованный пользователь может:

- выполнять все действия гостя;
- выбирать места и оформлять заказ;
- переходить к оплате;
- просматривать и редактировать профиль;
- просматривать историю своих заказов;
- менять пароль;
- привязывать Telegram-аккаунт;
- создавать заказы через API;
- отменять свой заказ через специальный API-метод `cancel`.

### 3. Менеджер

Менеджер в проекте реализован частично. В коде API есть permission-класс `IsManager`, который проверяет, что пользователь входит в группу `Manager`.

Менеджер может:

- создавать, изменять и удалять фильмы через API;
- создавать, изменять и удалять сеансы через API;
- просматривать все заказы через API;
- изменять и удалять заказы через API;
- отменять через API не только свои, но и чужие заказы.

Важно отметить, что отдельного веб-интерфейса менеджера, кроме Django Admin, в проекте не реализовано. Основная роль менеджера заметна именно в API-слое и через группы Django.

### 4. Администратор

Администратор — это суперпользователь Django.

Он может:

- входить в Django Admin;
- управлять всеми сущностями проекта;
- просматривать и редактировать модели;
- создавать и удалять записи;
- администрировать структуру контента и заказов.

## 7. База данных и модели

### Модель `Genre`

Назначение: хранит жанры фильмов.

Основные поля:

- `name` — название жанра.

Связи:

- связана с моделью `Movie` отношением many-to-many.

Роль в бизнес-логике:

- используется для классификации фильмов;
- участвует в фильтрации списка фильмов;
- отображается на страницах фильма и сеансов.

### Модель `Movie`

Назначение: хранит данные о фильме.

Основные поля:

- `title` — отображаемое название фильма;
- `original_name` — оригинальное название;
- `description` — описание;
- `duration` — длительность в минутах;
- `genre` — набор жанров;
- `release_date` — дата выхода;
- `age_limit` — возрастное ограничение;
- `poster` — постер;
- `slug` — уникальный slug для URL.

Связи:

- many-to-many с `Genre`;
- one-to-many с `Session`.

Роль в бизнес-логике:

- является базовой сущностью каталога;
- отображается в списке фильмов;
- используется при выборе сеансов;
- участвует в отображении заказов и билетов.

Дополнительная логика:

- валидация `original_name` на латинские символы;
- генерация `slug` через `slugify`;
- метод `get_absolute_url`.

### Модель `Hall`

Назначение: описывает кинозал.

Основные поля:

- `name` — название зала;
- `capacity` — вместимость зала.

Связи:

- one-to-many с `Session`.

Роль в бизнес-логике:

- определяет вместимость и количество мест;
- используется для расчёта списка доступных мест;
- участвует в отображении сеансов, заказов и билетов.

### Модель `Session`

Назначение: хранит конкретный сеанс фильма.

Основные поля:

- `hall` — зал;
- `movie` — фильм;
- `base_ticket_price` — базовая цена билета;
- `session_date` — дата сеанса;
- `start_time` — время начала;
- `end_time` — время окончания;
- `slug` — уникальный slug сеанса.

Связи:

- foreign key на `Hall`;
- foreign key на `Movie`;
- one-to-many с `Order`;
- one-to-many с `Ticket`.

Роль в бизнес-логике:

- является центральной сущностью для бронирования;
- используется при выборе мест;
- определяет цену и время показа;
- связывает фильм, зал и покупку.

Дополнительная логика:

- проверка, что цена положительная;
- проверка, что дата и время сеанса допустимы;
- вычисление `end_time` из длительности фильма;
- генерация slug;
- метод `get_available_seats`, который исключает билеты со статусами, отличными от `cancelled`.

### Модель `Order`

Назначение: хранит заказ пользователя.

Основные поля:

- `user` — пользователь;
- `session` — сеанс;
- `status` — статус заказа;
- `total_price` — общая стоимость;
- `created_at` — дата создания;
- `updated_at` — дата изменения.

Связи:

- foreign key на пользователя Django;
- foreign key на `Session`;
- one-to-many с `Ticket`.

Роль в бизнес-логике:

- объединяет купленные или зарезервированные места в один заказ;
- хранит итоговую сумму;
- участвует в логике оплаты;
- используется в профиле пользователя и в Telegram API.

Статусы:

- `pending` — заказ создан, но ещё не завершён оплатой;
- `completed` — заказ успешно оплачен;
- `cancelled` — заказ отменён.

### Модель `Ticket`

Назначение: хранит отдельный билет на конкретное место.

Основные поля:

- `session` — сеанс;
- `price` — цена билета;
- `seat_number` — номер места;
- `status` — статус билета;
- `user` — пользователь;
- `order` — заказ;
- `created_at`;
- `updated_at`.

Связи:

- foreign key на `Session`;
- foreign key на пользователя;
- foreign key на `Order`.

Роль в бизнес-логике:

- представляет одно конкретное место в рамках заказа;
- используется для контроля занятости мест;
- не позволяет продублировать место в одном сеансе за счёт уникального ограничения `session + seat_number`.

Статусы билета:

- `reserved` — место временно занято в ожидающем заказе;
- `booked` — место окончательно выкуплено;
- `cancelled` — билет отменён и место снова должно считаться свободным.

### Модель `TelegramProfile`

Назначение: связывает пользователя сайта с Telegram-аккаунтом.

Основные поля:

- `user` — пользователь;
- `telegram_id` — идентификатор Telegram;
- `verification_code_hash` — SHA-256 хеш кода подтверждения;
- `created_at`;
- `expires_at`;
- `is_used`.

Связи:

- one-to-one с пользователем Django.

Роль в бизнес-логике:

- обеспечивает привязку Telegram-аккаунта к сайту;
- хранит подтверждающий код в безопасном виде;
- ограничивает срок действия кода;
- позволяет Telegram API определить, какой пользователь связан с конкретным `telegram_id`.

### Связи между моделями

Основные связи в проекте:

- фильм связан с жанрами через many-to-many;
- сеанс связан с фильмом и залом;
- заказ связан с пользователем и сеансом;
- билет связан с заказом, пользователем и сеансом;
- `TelegramProfile` связан с пользователем через one-to-one.

## 8. Логика просмотра фильмов и сеансов

Пользователь попадает на список фильмов по маршруту `/movies/`.

Для этого используется класс [MovieListView](/F:/Python/Cinema/cinema_app/views.py), который:

- получает базовый queryset фильмов;
- считывает параметры `genre`, `age_limit`, `search`;
- передаёт их в сервис `get_movies_list`;
- возвращает отфильтрованный и отсортированный список.

Поиск работает по полям:

- `title`;
- `description`;
- `original_name`.

Фильтрация фильмов поддерживает:

- жанры;
- возрастное ограничение.

При открытии страницы фильма по slug используется `MovieDetailView`. На странице показываются:

- название;
- описание;
- длительность;
- жанры;
- дата выхода;
- возрастное ограничение;
- постер или изображение по умолчанию.

Список сеансов доступен по маршруту `/sessions/`. Также есть маршрут `/sessions/<slug>/`, который показывает сеансы конкретного фильма.

Логика `SessionListView`:

- выбираются сеансы с датой не раньше текущего дня;
- при наличии slug фильтрация идёт по конкретному фильму;
- поддерживается параметр даты;
- по умолчанию берётся текущая дата.

Таким образом пользователь может:

1. найти фильм;
2. открыть его страницу;
3. перейти к списку сеансов;
4. выбрать нужную дату и нужный показ.

## 9. Логика выбора мест

Логика выбора мест реализована вокруг модели `Session`, модели `Ticket`, шаблона [purchase_ticket.html](/F:/Python/Cinema/templates/payments/purchase_ticket.html) и view `purchase_ticket`.

Пошаговый сценарий выглядит так:

1. Пользователь выбирает конкретный сеанс.
2. Система определяет зал сеанса через связь `session.hall`.
3. Метод `Session.get_available_seats()` получает уже занятые или зарезервированные места.
4. Недоступными считаются места, по которым уже существуют билеты со статусом, отличным от `cancelled`.
5. В шаблоне строится сетка мест по 10 мест в ряду.
6. Пользователь видит свободные кнопки и недоступные кнопки.
7. При выборе мест JavaScript собирает их в массив `selectedSeats`.
8. Форма отправляет список выбранных мест в скрытом поле `selected_seats`.
9. На сервере система ещё раз проверяет актуальную доступность мест.
10. Если места всё ещё свободны, создаются заказ и билеты.

Защита от повторного выбора уже занятого места реализована двумя способами:

- серверной проверкой через `session.get_available_seats()`;
- ограничением базы данных `UniqueConstraint(fields=['session', 'seat_number'])`.

Это означает, что даже если два пользователя одновременно попытаются выбрать одно и то же место, на уровне данных дубликат не должен сохраниться.

Следует честно отметить, что проект не содержит сложного механизма распределённых блокировок или отдельной схемы “мягкой” конкурентной синхронизации. Но базовая защита на уровне проверки и уникального ограничения присутствует.

## 10. Логика заказов

Процесс создания заказа в веб-части реализован в `purchase_ticket_process` и `create_order_process` из [services.py](/F:/Python/Cinema/cinema_app/services.py).

Пошагово процесс выглядит так:

1. Пользователь выбирает одно или несколько мест.
2. Сервер получает список мест из POST-запроса.
3. Выполняется проверка, что места действительно выбраны.
4. Выполняется проверка, что эти места ещё свободны.
5. Внутри `transaction.atomic()` создаётся заказ.
6. Заказ получает статус `pending`.
7. Для каждого выбранного места создаётся билет со статусом `reserved`.
8. После этого вызывается логика оплаты.
9. Если ссылка на оплату сформирована, пользователь перенаправляется дальше.
10. Если оплата не инициализирована, возвращается сообщение об ошибке.

В API-части логика похожа, но реализована отдельным сериализатором `OrderCreateSerializer`.

Статусы заказа:

- `pending` — заказ создан, но ещё не завершён;
- `completed` — оплата подтверждена;
- `cancelled` — заказ отменён вручную или автоматически.

Смысл статусов:

- `pending` нужен для хранения временной резервации мест до подтверждения оплаты;
- `completed` означает успешную покупку;
- `cancelled` освобождает заказ и связанные с ним билеты.

## 11. Логика билетов

Билет создаётся как отдельная запись модели `Ticket` для каждого выбранного места.

Билет хранит:

- сеанс;
- заказ;
- пользователя;
- номер места;
- цену;
- статус;
- даты создания и обновления.

Статусы билета:

- `reserved` — место уже выбрано и добавлено в заказ, но оплата ещё не подтверждена;
- `booked` — билет выкуплен окончательно;
- `cancelled` — место освобождено.

Разница между `reserved` и `booked`:

- `reserved` — промежуточное состояние перед подтверждением оплаты;
- `booked` — окончательное оплачиваемое состояние.

При успешной оплате:

- заказ получает статус `completed`;
- все билеты заказа переводятся в статус `booked`.

При отмене заказа или его автоматическом закрытии:

- заказ переводится в `cancelled`;
- билеты переводятся в `cancelled`.

## 12. Отмена неоплаченных заказов

В текущей учебной версии для отмены неоплаченных заказов используется management command [cancel_unpaid_orders.py](/F:/Python/Cinema/cinema_app/management/commands/cancel_unpaid_orders.py).

Она работает следующим образом:

- ищет заказы со статусом `pending`;
- сравнивает `created_at` с текущим временем;
- по умолчанию использует порог 15 минут;
- для просроченных заказов переводит связанные билеты в `cancelled`;
- затем переводит сам заказ в `cancelled`;
- выводит количество отменённых заказов в консоль.

Эта команда нужна для учебной демонстрации логики “очистки” неоплаченных резерваций без запуска фоновой инфраструктуры.

В проекте также остался файл [tasks.py](/F:/Python/Cinema/cinema_app/tasks.py), где логика отмены заказов может быть использована как Celery-задача. Это дополнительный вариант автоматической фоновой обработки. Однако в локальной учебной версии Celery не обязателен, и для курсовой достаточно management command.

## 13. Оплата через Stripe

Stripe используется для организации внешнего платёжного сценария.

Основная логика оплаты находится в [services.py](/F:/Python/Cinema/cinema_app/services.py):

- создаётся Stripe Checkout Session;
- в неё передаются позиции по каждому билету;
- указывается `client_reference_id`, равный `order.id`;
- задаются `success_url` и `cancel_url`.

В платёжную сессию передаются:

- режим оплаты `payment`;
- идентификатор заказа;
- список `line_items`;
- информация о каждом билете;
- цена каждого билета;
- описание фильма, сеанса и места.

После инициализации оплаты пользователь перенаправляется на Stripe Checkout.

После успешной оплаты пользователь попадает на промежуточную страницу `purchase_pending`, где фронтенд периодически опрашивает endpoint статуса заказа `/order-status/<id>/`. Как только заказ становится `completed`, пользователь автоматически перенаправляется на страницу успешной покупки.

При отмене оплаты пользователь попадает на страницу отменённой оплаты, откуда может вернуться на главную страницу или повторить оплату.

Подтверждение успешной оплаты выполняется в [webhooks.py](/F:/Python/Cinema/cinema_app/webhooks.py):

- Stripe присылает webhook;
- проверяется подпись события;
- обрабатывается событие `checkout.session.completed`;
- по `client_reference_id` находится заказ;
- если `payment_status == paid`, заказ переводится в `completed`;
- связанные билеты переводятся в `booked`.

Важно отметить:

- в локальной учебной версии Stripe-ключи не обязательны;
- если ключи не заданы, сайт всё равно запускается;
- обычные страницы не падают;
- интеграция оплаты может использоваться как демонстрационная.

## 14. Telegram-интеграция

Telegram-бот в проекте является дополнительным модулем.

Его назначение:

- дать пользователю альтернативный способ получить часть данных о своём аккаунте;
- показать заказы и профиль через Telegram;
- реализовать привязку Telegram-аккаунта к сайту.

### Как происходит привязка аккаунта

1. Пользователь на сайте открывает профиль.
2. Если Telegram ещё не привязан, ему доступна ссылка `Telegram Link`.
3. При запуске привязки создаётся запись `TelegramProfile`.
4. Генерируется цифровой код.
5. В базе сохраняется не сам код, а его SHA-256 хеш.
6. Для кода задаётся срок действия.
7. Пользователь либо получает deep-link к боту, либо проходит привязку через email-код.

### Почему код хранится в хешированном виде

Это сделано для повышения безопасности. Даже если кто-то получит доступ к базе, он не увидит исходный код подтверждения в открытом виде.

### Проверка срока действия

Модель `TelegramProfile` хранит поле `expires_at`. Метод `is_valid()` возвращает `False`, если:

- код уже был использован;
- срок действия истёк.

### Как бот получает профиль и заказы

Telegram-бот не работает напрямую с базой. Он обращается к API сайта через `httpx`.

Основные запросы бота:

- подтверждение привязки;
- проверка факта привязки;
- получение профиля пользователя;
- получение списка заказов;
- запрос кода привязки по email.

### Используемые API endpoints

- `/api/telegram/link/confirm/`
- `/api/telegram/link/check/<telegram_id>/`
- `/api/telegram/user/info/<telegram_id>/`
- `/api/telegram/user/orders/<telegram_id>/`
- `/api/telegram/send-email/`

### Состояние Telegram-модуля

Telegram-бот реализован частично:

- сценарии привязки, чтения профиля и заказов присутствуют;
- меню пользователя и гостя реализованы;
- обработчик фильмов пока представляет собой заглушку;
- обработчик сеансов фактически не активен.

Важно отметить, что Telegram-модуль является дополнительным. Основной сайт должен запускаться и работает без Telegram token.

## 17. Безопасность

В проекте используются следующие механизмы безопасности.

### Django Auth

Используется встроенная система пользователей Django.

### `login_required`

Декоратор применяется для защиты функций:

- покупки билетов;
- повторной оплаты;
- Telegram-привязки.

### `LoginRequiredMixin`

Используется в:

- профиле пользователя;
- настройках профиля;
- списке заказов.

### CSRF-защита

Обычные формы Django защищены CSRF-механизмом.

Исключение:

- Stripe webhook помечен `@csrf_exempt`, что нормально для внешнего webhook endpoint.

### Проверка владельца заказа

В веб-части есть проверки, что пользователь может видеть только свой заказ:

- в `purchase_success`;
- в `purchase_cancel`;
- в `check_order_status`.

### Права доступа API

В API применяются:

- `IsAuthenticated`;
- `IsAuthenticatedOrReadOnly`;
- `IsManager`.

### Группы и менеджерские права

Менеджерская роль завязана на группу `Manager`.

### Хеширование Telegram-кодов

Коды привязки Telegram не хранятся в открытом виде. Используется SHA-256.

### Срок действия Telegram-кодов

Код ограничен по времени через `expires_at`.

### Проверка Stripe webhook

Webhook проверяет подпись события Stripe.

### Честная оценка

Некоторые механизмы безопасности реализованы базово, но не максимально глубоко:

- нет сложного антиконкурентного механизма на уровне очередей;
- часть Telegram API открыта с `AllowAny`, так как ориентирована на Telegram-сценарии;
- менеджерская роль есть в API, но отдельный полноценный пользовательский интерфейс менеджера не реализован.

- PostgreSQL или другая более подходящая БД;
- отдельная схема деплоя;
- реальные Stripe-ключи;
- Telegram token;
- фоновые сервисы для автоматических задач;
- более серьёзная обработка конкурентных бронирований.

## 21. Итог

Проект `Cinema` представляет собой учебную информационную систему для онлайн-бронирования билетов в кинотеатр. В нём реализованы основные сущности предметной области: фильмы, жанры, залы, сеансы, заказы, билеты и пользовательский профиль с возможностью Telegram-привязки.

Проект решает задачи:

- публикации киноафиши;
- просмотра сеансов;
- выбора мест;
- оформления заказов;
- сопровождения статусов оплаты;
- хранения истории заказов;
- предоставления данных через API.

Для курсовой работы проект подходит, потому что объединяет:

- Django-модели и ORM;
- веб-интерфейс;
- авторизацию;
- REST API;
- интеграцию со Stripe;
- Telegram-модуль;
- административную часть;
- management commands;
- расширяемую архитектуру.

Таким образом, `Cinema` можно рассматривать как цельный учебный проект, демонстрирующий как построение веб-приложения на Django, так и интеграцию внешних сервисов и дополнительных клиентских модулей.
